大模型的上下文

Context Window：模型一次"看得见"的全部内容  ｜  全部内容可点击出处验证

01 · 它是什么

上下文窗口是模型单次调用能处理的最大 token 范围——所有内容都在这一个"窗口"里。

关键事实：窗口内一切内容（指令、历史、资料）共同占用容量，且每一轮都要重新送入 —— Lilian Weng：短期记忆即上下文学习 ↗

个人解释

我看来它像是一个短期存储的 U 盘，里面装着跟模型交代过的上下文。能联系上下文的模型很棒——这样再提到前面说过的东西时，就不用重新介绍一遍了。

03 · 核心机制：位置决定利用率

"Lost in the Middle" 的核心发现：相关信息在开头或结尾时表现最好，落在中间时显著下降。

结论来自多文档问答与键值检索两组实验，长上下文模型也不例外 —— 论文 ↗

04 · 最小示例：一次调用的拼装

POST /messages
{
  "system": "你是统计学学习助手……",        ← 常驻，优先级最高
  "messages": [
    {"role": "user", "content": "什么是假设检验"},   ← 历史轮次
    {"role": "assistant", "content": "假设检验是……"}, ← 全部重发
    {"role": "user", "content": "给我举个例子"}        ← 新消息
  ]
}
# 三部分共同占用上下文窗口；历史越长，成本越高，窗口越满

token 计量与窗口管理细节见各模型官方文档（此示例为通用 Messages API 结构）

05 · 应用场景与边界

具体应用场景

长文档问答：把与问题最相关的段落放在开头或结尾，而不是塞在中间——同样的内容，换位置就能明显提升回答质量（这是对 Lost in the Middle 结论的直接应用）。

容易混淆 / 使用边界

易混淆点澄清
上下文 ≠ 记忆会话结束后即消失；跨会话的"记忆"要靠外部存储 + 检索（Agent 的长期记忆）
窗口大 ≠ 用得好窗口再大，中间信息利用率照样下降；"塞得进"不等于"用得上"
上下文不是免费的输入 token 按量计费，历史每轮重发，长对话成本线性增长
